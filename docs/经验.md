# 开发经验

最后更新：2026-08-23

本文件只记录容易复发，并会影响安全、验证有效性或开发效率的经验。一次性问题、开发流水账和可从代码直接确认的事实不写入此处。

## 工具与实机验证

- Obsidian CLI 必须在容器外的宿主机终端运行；容器内终端不可用，不要反复绕道尝试。用户已授权使用容器外终端执行 Obsidian CLI。
- CLI 的 Vault 选择器必须写在子命令之前，例如 `obsidian vault=Obsidian-repo plugin:reload ...`；写在子命令之后会被忽略。操作前用 `obsidian vault=<名称> vault info=path` 核对实际路径。
- 优先使用自动化测试、Obsidian CLI 和可重复的只读检查。Computer Use 只在必要的视觉或交互验收中使用，并尽量减少步骤和次数。
- 构建产物更新后必须重载插件或 Obsidian 再验收。用户已授权自主 force reload，但重载前仍需避免覆盖未保存编辑。
- 覆盖 `main.js` 后若行为仍像旧版，先核对产物哈希，再完整退出并重开 Obsidian；`⌘R` 可能只刷新界面而未卸载旧插件实例。
- 工具尝试无果时，在有限次数后如实标记阻塞；不要为了规避真实限制反复绕路消耗时间和 token。

## 数据与同步安全

- `ObDevTestVault` 内的 Helix 测试数据可以增删改；正式 Obsidian 仓库的数据和用户已有滴答对象不得用于测试或清理。
- 真实滴答写入只使用名称唯一、边界明确的专用临时对象，并在确认远端身份后精确清理；远端结果未知时禁止盲目重试。
- 保留 API 口令不等于已启用写入。新设备、新 Vault、口令变化或合同版本变化后，必须重新确认认证与写入能力。
- 写入合同夹具必须满足生产投影的真实前置条件；例如远端父任务只为“进行中” Stage 创建，夹具 Stage 也必须先进入进行中。
- 旧 Markdown 可能同时存在复选框状态不一致与失联父引用。迁移应分步修复、最后统一严格校验，不能让首个错误阻断后续可恢复问题。
- 反向同步必须同时读取活动任务与“已完成任务”接口；清单详情通常不含已完成任务，合并时以清单详情覆盖同 ID 缓存，才能正确处理重新打开。
- 远端状态必须进入自动同步候选指纹；只比较 Markdown 会漏掉纯远端变化。普通同步发布状态早于授权锁释放时，应延后一拍再计算项目同步就绪条件。
- 网络请求不得占用项目工作区的全局 mutation runner；远端同步使用独立串行器，Markdown 落盘再做 CAS，避免整个 Helix 随网络延迟冻结。

## 布局与交互测试

- 验证自动布局时，先记录目标节点的基准位置 A；每个后续场景开始前都恢复到 A，否则自动整理会让位置对比失效。
- 能用领域测试、DOM 检查或 CLI 验证的行为，不使用 Computer Use；只有视觉层级、拖拽、悬停等真实交互才做最小化实机验收。
- Obsidian `Setting` 的 builder 回调会同步执行；需要引用 Setting 自身时先完成变量声明，再调用 `addButton` 等 builder，避免暂时性死区导致整个设置页中断。

## Git 与发布

- 日常开发和修复只在 `dev`。只有用户明确说“发布新版”，才允许合入 `main`、创建标签和 Release。
- 阶段验证通过后再提交；保护工作树中不属于当前任务的修改，不静默覆盖或清理。
